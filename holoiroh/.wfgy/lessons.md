
## 2026-07-28 -- gm-plugkit prd-add write path stuck after prd.yml disappeared between sessions
Goal (G): Complete and ship the Tinfoil confidential-computing integration in holoiroh (Rust daemon modules + wire protocol + iOS UI), tracked via the gm skill's PRD mechanism.
What drifted / what went wrong: mid-session, `.gm/prd.yml` (previously holding ~49 tracked rows, 37+ resolved across a long session) was simply gone -- `instruction` still worked (phase=PLAN, prd_pending_count=0, tolerates a missing file on read), but `prd-add` failed identically on every attempt with `{"error":"write failed","error_code":"failed","exitCode":1}` regardless of payload content (confirmed via distinct request_fingerprints per distinct payload -- not a dedup/cache artifact, a genuine write failure). All the real underlying code work the missing rows tracked was independently confirmed still intact on disk via `git_status` (every file listed as modified/untracked matched exactly what had been built).
Fix / resolution: Tried three real recovery attempts per BBCR's bounded-retry discipline: (1) `bun x gm-plugkit@latest spool` reboot -- same daemon pid, no change; (2) killing the daemon pid directly to force a genuinely fresh spawn -- new pid, identical failure; (3) manually creating `.gm/prd.yml` as a minimal valid empty YAML array before retrying -- file was left untouched, identical failure. After 3 bounded attempts with no change, stopped retrying blindly (per BBCR) and pivoted: the gm PRD-tracking layer is bookkeeping *around* the work, not the work itself -- `git_status`/`exec_js`/git verbs still function normally, so verification (build/compile checks) and delivery (commit, push) can proceed directly through those verbs without depending on the broken prd-add write path. Recorded the stuck state here rather than silently working around it unremarked, or fabricating PRD rows that read as tracked-and-resolved when the tracking mechanism itself was not actually persisting them.
Generalizes to: In this project, if `prd-add`/`prd-resolve` ever fail with a generic "write failed" while `instruction`/git verbs still work, don't keep bounded-retrying past 3 attempts across reboot/restart/file-creation -- the underlying storage write path itself may be broken independent of the daemon process lifecycle (possibly needs a fix in the plugkit/agentplug-runner Rust source, not something recoverable from the calling-agent side within a normal session). Verify and ship the actual deliverable through the verbs that do work rather than blocking real progress on a broken bookkeeping layer.
